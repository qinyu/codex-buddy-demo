# product-workflow 章程规则源（charter-rules.md）

本文件是项目章程（客户 `AGENTS.md` 托管块）的**单一规则源**。托管块的生成、升级只从本文件整块重渲染；块内不单独维护规则正文。

## 托管块机制

- 客户项目 `AGENTS.md` 中由套件维护的内容放在一个集中托管块里，块界标记：

  ```markdown
  <!-- BEGIN product-workflow charter suite=v<当前 VERSION> -->
  ...（块内容）
  <!-- END product-workflow charter -->
  ```

- 块级版本标记 `suite=vX.Y.Z` 是唯一版本记录；实际值必须取套件根目录 `VERSION` 首行（现行 `product-workflow-X.Y.Z`，旧包 `haitian-pw-X.Y.Z` 仍可读）。迁移器同时写 `source-sha256` 校验托管块是否被人工修改。块内规则不打逐条版本标签。升级时运行 `migrate_suite.mjs` 整块刷新，不做块内逐条合并。
- 块外是用户内容，套件不触碰、不重排、不改写。
- 安装或升级前先读用户既有 `AGENTS.md`（含客户自己写的原文）：逐条语义比对，用户条款已覆盖的规则**跳过不注入**，并在 profile 中记录「已由用户条款覆盖」；通用智慧（怎么做事、先读再写等与本项目无关的通用条）一律不注入。
- 用户改过块内内容时：报冲突、列出差异，等用户裁决；**不得静默覆盖**。

## 规则范围三类

| 类别 | 例子 | 注入策略 |
|---|---|---|
| product-workflow 特有 | 豁免口径、状态转移、切片工作流 | 始终注入 |
| OS 与操作约束 | Windows 写入（R08）、编码跟随（R07） | 按目标环境注入 |
| 栈特定 | 前端设计系统、WPF/XAML | 按仓库 profile 注入 |

套件组装机制（两种模式/外挂/门户）属机制决策，不进托管块；决策依据见套件仓 `docs/adr/0003-suite-assembly-two-modes-addons-portal.md`（仅套件维护者视角可达，客户环境无套件仓）。

## 规则清单

每条规则含 ID、正文、注入起始版本、来源依据。正文是权威表述；托管块里只出现短句形式，细则以本文件为准。

### R07 编码跟随（suite=v0.4.0 起）

正文：

- 修改已有文件前，先探测该文件当前编码（BOM、GBK/GB18030、UTF-8），**跟随原编码读写**；不要把 GBK 存量文件按 UTF-8 打开或保存。
- 新建文件一律 UTF-8 无 BOM。
- 编码检查、BOM 清理只针对本次改动清单内的文件；**禁止全仓扫描**。
- 遇到乱码先怀疑读取代码页不匹配，而不是先改文件内容。

操作细则（探测命令示例，环境即事实源，优先实测）：

- PowerShell 5.1 判定：`$PSVersionTable.PSVersion.Major -lt 6`。
- PowerShell 5.1 写 UTF-8 无 BOM：`[IO.File]::WriteAllText($path, $text, [Text.UTF8Encoding]::new($false))`；读 GBK：`[IO.File]::ReadAllText($path, [Text.Encoding]::GetEncoding(936))`。
- BOM 探测：读文件头 3 字节是否为 `EF BB BF`。
- GBK/UTF-8 严格解码探测：先按 UTF-8 严格解码，失败再按 GB18030 严格解码，都失败时停下来问用户，不要猜。
- 乱码处理：先确认原编码，再决定是「按原编码重读」还是「用户批准后转码」；不得直接用替换字符覆盖保存。

来源：问题 #42（Java 存量 GBK 文件按 UTF-8 读写乱码）、#44（编码修正 8 分钟空转）、#37（编码约定未落地）。

### R08 Windows 写入（suite=v0.4.0 起；目标环境为 Windows 时注入）

正文：

- Windows 沙箱环境下**不用 apply_patch 写文件**（ unelevated 沙箱会拦截，失败链会拖慢数分钟）；用原生写入：PowerShell `Set-Content`/`Out-File`（显式指定编码）或 `[IO.File]::WriteAllText`。
- 写入显式指定编码；目标是 UTF-8 无 BOM 时用 `[IO.File]::WriteAllText` + `UTF8Encoding($false)`。
- 同一文件同一写入操作**连续失败 2 次即停下**，向用户报告已试通道与报错；禁止换第四五种工具继续空转。
- 批量写入合并成一个脚本一次执行，不逐文件发起多轮写入。

来源：问题 #38（apply_patch 被沙箱层层拦截后连环换工具）、openai/codex#34294（Windows unelevated 沙箱 apply_patch Access Denied，OPEN 无官方修复）。

### 状态转移（suite=v0.4.0 起）

正文：

- 阶段状态枚举：`Draft` / `Reviewed` / `Blocked` / `Not Generated` / `Not Applicable`。
- AI 只能把状态写为 `Draft` / `Blocked` / `Not Applicable`（含 Not Generated）；`Reviewed` 是**人专用**状态，只有用户明确批准后才能写入。
- 已批准产物再次修改时：状态回 `Draft`，并在 `.workflow-state.json` 该阶段对象上加 `"revising": true`，看板徽章「已回改待复审」据此派生；复审通过写回 `Reviewed` 并移除 `revising`。

来源：收工状态疑问（用户问「Reviewed 谁写的」）；0.3.0「未跑通不得标已通过」的同族规则。

### 工作流短句（suite=v0.4.0 起）

- 新切片走产品工作流；阶段深度按切片裁剪：可跳过（Not Applicable）、可复用已批准产物、可轻量合并；PRD 与开发计划必有，允许轻量形态。
- 豁免可先写业务代码；测试状态如实标注，跑通的才算通过。
- 遗留套件走增量覆盖：新增代码必须有单测；不可测的遗留行摊给用户，默认窄排除，不为追覆盖做可测试性大重构。细则见 unit-test-generator 的 mode0-diagnosis.md。
- 开发完成后回写文档与状态。
- 中文输出、中文注释。
- 三方 skill 按时机调用：项目级初始化做一次并复用；需求级按阶段接入。不要每个切片都重跑对方的全流程。
- 交付件分层存放：进代码仓的资产与进度记录分开；项目级长期维护，需求级按切片保存。不要把进度状态和一次性文档一律提交到 docs。
- 门户时机（选用门户时）：阶段写成 Draft / Reviewed 不是自动上传。开工硬卡通过后自动同步一次，然后给人交付物页去定稿并确认开工。切片实现收尾：先写 `slice_wrap_up`；绑了门户再报任务完成，给人交付物页请全员确认收工。阶段评审收尾不写这一笔。对人说人话和链接，不念命令。不选门户时不调 `limix`。
- 能脚本生成或校验的文件不要手写：状态 JSON、配置 schema、看板壳、目录清单。AI 只写判断性正文。

### 行文与排版（suite=v0.5.0 起；工作坊材料与给人看的产物现在就要遵守）

正文：

- 给人看的文字要好懂：先说结论，再用证据；像人说话，不像通告。
- 一句说一件事。能短则短，能表则表，不要堆口号、排比、空泛收口。
- 同等元素用接近的字数和同一句式，例如表格两列、并列按钮、步骤标题。
- 换行看整行：最后一行不要只剩一两个字；标题、卡片、按钮尤其要避开这种孤行。
- 会话总结、工作坊口播、可转发介绍，都要能单独读懂：版本、做什么、怎么装、不做什么。
- 评测和进展分层写，不混算、不把正确阻断写成已完成。

来源：2026-09-01 工作坊准备沟通；咨询仓文档规范「结论先行 / 表格优先」；给人看的介绍要可转发。

### 设计上下文（suite=v0.5.0 起）

- 原型或界面实现前必须先读现有 UI、设计系统、token、组件、截图说明和项目根 `DESIGN.md`（如有）；没有证据不得自创视觉体系。
- 探测到 impeccable skill 或项目已有 `PRODUCT.md` / `DESIGN.md` 时按项目级接入：Setup（`$product:setup`）对应 `PRODUCT.md`，用户选择Wiki整理设计知识时引用 `DESIGN.md`；后续切片只读复用，不反复重跑。
- `PRODUCT.md` 是用户、任务、平台和约束的事实源；project-profile 只引用，不复制。`DESIGN.md` 是设计事实源；PRD/原型/实现只引用本切片相关约束。
- 未探测到 impeccable 时不提示安装，仍跟随项目现有设计证据；找不到则标缺口。

### 输入（suite=v0.4.0 起）

- 有效稿、图/原型与未读信息按公共契约 § 有效输入与缺失信息处理执行；不把修订原件或二手图片描述当成已确认依据。

### 跟随现状（suite=v0.4.0 起；类别式规则 + 举一反三元规则）

- 版本与依赖只增不改：语言 SDK 与运行时、包管理器、框架、依赖、构建脚本与 wrapper 一律沿用仓库现有版本；新依赖增量添加，选型在现有版本基础上做。JDK / Maven / npm / pip / Gradle 等均为示例，**不穷尽**。
- 编码跟随文件现状（细则 R07）。
- 风格跟随现有系统：原型与界面改动以现有设计系统为准。
- 检查范围跟随变更清单：编码、BOM、格式检查只查本次改动文件。

举一反三元规则（放托管块顶部）：**规则按类别适用，示例仅示意不穷尽；同类工具、依赖、构建脚本、wrapper 一律适用同一原则。**

来源：0.3.0「门禁只增加」决策的类别化改写；评审意见（防字面锚定，模型看到 Maven 就只对 Maven 生效、看到 pip 不生效）。
