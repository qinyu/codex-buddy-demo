# 项目初始化与工作区准备 ($product:setup)

`product-workflow-0.9.3`

在代码仓中第一次使用产品研发工作流，或者面对一个全新的空目录、需要拉取代码并确立团队规范时，使用本技能完成初始配置。它是全量与轻量工作流运行的前置环境准备，**一次配置，后续所有需求自动继承**。

---

## 核心思路：Setup 是项目级事实，不是每个需求重复跑

很多工程师刚接触时会有疑问：*“我每次来一个需求，都要把 Setup 从头跑一遍吗？”*

> 💡 **底层生命周期机制：项目级（一次性） vs 业务切片级（日常轮转）**
> - **跨需求共享事实**：`AGENTS.md`（项目章程）、`.product-workflow-config.json`（工作流策略配置）和 `docs/wiki/`（项目知识库）保存在代码仓根目录。一个项目在生命周期中**只做一次 `$product:setup`**。
> - **后续需求自动静默校验**：后续无论是做第 10 个小改动还是第 100 个大功能，直接运行 `$product:workflow` 即可。工作流编排器在启动时虽然会检查根目录配置，但**检测到配置有效后直接静默跳过交互**，直接进入需求分析，绝不会每次都重复盘问一遍技术栈、代码许可或门户地址。
> - **何时需要重新跑？**：只有在项目技术架构发生重大重构、调整了多仓目录边界，或团队想要修改全仓门禁策略（如单测门禁改强制）时，显式执行 `$product:setup --refresh` 进行增量刷新即可。

---

## 一、从零开始：工作区识别与单仓/多仓授权拉取

面对一张白纸（全新空目录或只有设计文档的目录），直接向助手提供仓库地址即可开启初始化。

> 💡 **底层安全机制：两段式授权拉取时序**
> 面对全新目录，`$product:setup` 严格遵循“先登记求证、经授权后拉取”的安全边界：
> 
> ```mermaid
> sequenceDiagram
>     autonumber
>     actor User as 开发者 (你)
>     participant Setup as $product:setup (技能)
>     participant Script as 探测脚本 (只读探测)
>     participant Git as 本机 Git 与凭据助手
> 
>     Setup->>Script: 1. 探测工作区目录状态
>     Script-->>Setup: 检查 .git 与文件，输出 awaiting-authorized-clone
>     Note over Script: 严格只做探测与登记，绝不私自 clone
> 
>     Setup->>User: 2. 核对授权：展示仓库地址、落点目录并求证
>     User-->>Setup: 明确授权确认
> 
>     Setup->>Git: 3. 安全拉取：执行 Git Clone
>     Note over Git: 沿用本机 SSH 密钥或凭据助手，免明文认证
>     Git-->>Setup: 代码拉取成功
> 
>     Setup->>Setup: 4. 识别项目根边界，定稿 AGENTS.md 章程
>     Setup-->>User: 工作区就绪，配置全仓继承
> ```

### 1. 单仓库场景
如果你的项目只有一个代码仓库，向助手提供仓库地址即可：
```text
帮我初始化工作区，从 git@github.com:your-org/main-service.git 拉取代码。
```
助手会核实目录为空后，在取得你同意后拉取到本地，并基于代码内容建立初始化配置。

### 2. 多仓库协同场景 (Multi-repo)
如果大型业务由前端、后端、公共契约等 3~5 个独立 Git 仓库组成，你只需准备一份简单的仓库映射清单（如 `workspace.json`）：
```json
{
  "repositories": {
    "web-frontend": { "url": "git@github.com:your-org/web.git", "branch": "main" },
    "api-backend": { "url": "git@github.com:your-org/backend.git", "branch": "master" }
  }
}
```
执行：
```text
$product:setup 请按照 workspace.json 登记并拉取多个协同代码仓。
```
Setup 会通过底层脚本分别核实每个子目录，在不破坏已有代码的前提下逐个安全拉取，确立统一的跨仓开发根目录。

> ⚠️ **安全红线：脚本只登记，拉取必须经你授权**
> 底层探测脚本严格遵守安全设计：它只做目录探测与状态登记，**坚决不私自执行 clone，也不安装任何依赖**。所有 Git 拉取动作必须向你明确展示仓库来源与本地落点、获得确认后才执行，并且全程复用本机安全凭据，防止代码泄露与环境污染。

## 二、调用方式：主动点名与被动推荐

- **主动调用（人触发）**：
  新拉取项目或想重新梳理章程时，在终端或聊天框中输入：
  ```text
  $product:setup
  ```
  或者自然语言开口：
  ```text
  帮我初始化一下当前代码仓的产品工作流配置。
  ```
- **被动推荐（流程硬门禁）**：
  直接运行 `$product:workflow` 时，如果根目录缺少 `.product-workflow-config.json`，工作流会强制暂停并提示：“*当前代码仓尚未初始化，请先执行 `$product:setup` 确立项目配置。*”

## 三、准备范围选择：最小准备 vs 完整工作流配置

| 准备模式 | 适用场景 | 交付产物与要求 |
|---|---|---|
| **最小准备 (Minimal)** | 临时仓库、紧急排障、只想确立基本规范，不需要复杂的门禁和流水线。 | 只定稿有效的 `AGENTS.md`。不强制要求 Git、不要求门户、不生成 profile 和状态索引。 |
| **完整配置 (Full)** | 团队正式项目、需要跑完整产品需求或轻量交付的长期维护代码仓。 | 生成 `.product-workflow-config.json` 与 `docs/product-workflow/project-profile.md`，定稿完整 `AGENTS.md`。 |

## 四、基建准备阶段的“外挂穿插机制”

在进入具体需求之前，`$product:setup` 负责穿插和调度针对整个代码仓的基础能力：

1. **穿插代码仓架构与知识库构建 ($wiki)**：
   Setup 评估当前仓库知识缺口。代码拉取到位后，建议调用 `$wiki` 技能提取依赖拓扑与领域模型，整理业务术语表，作为后续全流程只读引用的事实底座。
2. **穿插前端设计规范协同 (impeccable)**：
   自动只读探测项目根目录是否存在 `PRODUCT.md`（产品意图源）或 `DESIGN.md`（视觉与组件规范源），记录入口，为后续界面开发确立设计约束。
3. **穿插单元测试与本地拦截防线**：
   检查当前仓库是否具备自动化测试基建。若缺少单测运行环境或 Git 拦截机制，引导通过 `$unit-test-init` 生成原生测试脚本，并通过 `$git-hook-init` 建立提交拦截防线。

## 五、助手会提问什么，你该怎么配合回答

在执行过程中，助手把关以下核心决定，你只需要按意图简单回复：

### 1. 决定一：项目阶段与模式（从零研发 vs 存量增量迭代）
- **助手的提问方式**：
  > “我检测到当前仓库已经有较为完整的业务代码。本次是为**既有项目做存量增量迭代**，还是把当前仓库当做**全新的 0 到 1 项目**重新规划？”
- **你的回答方式**：
  - 老项目日常维护：`既有项目增量迭代`（将 `product_mode` 设为 `existing_iterative`）
  - 全新项目起步：`从零开始做新项目`（将 `product_mode` 设为 `greenfield_first`）

### 2. 决定二：代码探查许可（是否允许助手自主检索代码）
- **助手的提问方式**：
  > “在后续分析需求、撰写技术方案和拆解任务时，是否允许助手自主检索和读取仓库内的源码以保障方案准确性？”
- **你的回答方式**：
  - 推荐选择：`允许`（设置 `code_exploration: "allowed"`，避免助手凭空造轮子）
  - 保密限制：`不允许，只看我提供的文档`（设置 `code_exploration: "user_declined"`，后续助手严禁静默读代码）

### 3. 决定三：交付记录偏好（纯本地离线 vs 团队门户同步）
- **助手的提问方式**：
  > “后续需求的交付材料是**完全保存在本地目录**，还是需要**配置 Limix 研发看板地址进行同步**？”
- **你的回答方式**：
  - 纯本地开发：`仅保存在本地`（`portal_sync: "off"`）
  - 团队看板同步：`需要同步，门户地址是 https://your-domain.com`

## 六、关键产物全貌

| 产物文件 | 存放位置 | 核心作用与内容 |
|---|---|---|
| `AGENTS.md` | 仓库根目录 | **项目章程文件**。在托管区域清晰记录用户的代码探查许可、Wiki 选择及项目稳定约束。 |
| `.product-workflow-config.json` | 仓库根目录 | **工作流机器配置**。记录 `product_mode`、`code_exploration`、测试及自动化门禁策略。 |
| `project-profile.md` | `docs/product-workflow/` | **项目档案文档**。人类可读，记录技术栈、现有代码结构、部署边界与遗留未决项。 |

> 📌 **关键产物：托管区域隔离与冲突保护**
> `AGENTS.md` 采用特殊的托管标记块来记录由 `$product:setup` 维护的规则。你自己在 `AGENTS.md` 中编写的个性化开发提示词和工程规则绝不会被冲掉。
