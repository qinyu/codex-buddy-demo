# 交互原型制作指南 ($product:prototype)

`product-workflow-0.9.3`

在开发涉及用户界面的新功能时，仅靠文字需求往往难以直观评估交互流转。交互原型制作技能负责生成自包含的单文件交互原型（`prototype.html`），让你和团队在动代码前就能直观体验产品流程。

---

## 一、解决什么问题

对于复杂的前端界面与多步操作流程：
- 仅看文档容易产生理解偏差，直到开发完成看到界面才发现布局不合理、交互别扭；
- 缺少可点击的原型，需求方与设计人员很难提前核对关键状态（如空状态、加载态、表单校验错误提示）；
- 传统原型工具需要切换平台或登录外部协同软件，增加了沟通成本。

`$product:prototype` 直接在本地切片目录下生成一个**纯静态、自包含、可交互的 HTML 原型文件**，双击即可在浏览器中试用。

> 💡 **底层模拟机制：自包含本地模拟器架构**
> 
> 生成的原型专为本地离线评审打造，具备以下架构特征：
> 1. **单文件自包含**：HTML、CSS 布局与 JavaScript 状态均内联在单个文件中，不发外部网络请求，不依赖后台 API，支持无网络离线演示；
> 2. **真实交互状态模拟**：内置轻量状态机，支持按钮点击、标签页切换、输入框表单校验以及模拟数据展示；
> 3. **无缝嵌入评审看板**：生成的原型通过 iframe 原生内嵌在本地评审看板（`.review-board/index.html`）中，评审时无需切换窗口。
> 
> ```mermaid
> flowchart TD
>     PRD["1. 读取已批准需求文档 (prd.md)"] --> Extract["2. 提取用户旅程与界面交互节点"]
>     Extract --> GenHTML["3. 编写单文件自包含 prototype.html"]
>     GenHTML --> Preview["4. 浏览器本地交互试用与体感对齐"]
>     Preview --> Approve{{"5. 人工审阅确认并批准 (Reviewed)"}}
> ```

## 二、怎么对助手开口

用自然的工程语言提出原型设计需求：

```text
根据刚刚通过的需求文档，帮我做一份商户对账单筛选的交互原型，要求可以切换日期范围并查看表格空状态。
```

或者明确指定样式与组件规范：

```text
按已有的 DESIGN.md 规范，把结算页新增发票抬头的交互原型做出来，包含个人和企业两种抬头的表单切换。
```

## 三、适用场景与自动裁剪规则

并非所有需求都需要制作原型，工作流遵循按需裁量原则：

| 业务场景 | 是否需要制作原型 | 状态机流转与处理方式 |
|---|---|---|
| **新增页面、全新复杂交互、多步向导** | **需要** | 状态设为 `Draft`，生成 `prototype.html`，供人工体验后批准为 `Reviewed`。 |
| **纯后端接口、底层数据处理、脚本任务** | **无需制作** | 系统自动在 `.workflow-state.json` 中标记为 `Not Applicable`，**原因注明 `纯后端/无界面`**，坚决不造空壳文件。 |
| **轻量工作流 (Lite)** | **默认裁剪** | 小需求直接标记为 `Not Applicable`，快速进入开发。 |

---

## 四、关键产物：`prototype.html`

原型生成的产物保存在当前切片目录下：`docs/product-development/YYYY-MM-DD-<需求名称>/prototype.html`。

人工在浏览器中试用体验无误后，在对话中确认批准，该阶段状态流转为 `Reviewed`。若团队使用的是 Stitch 自动化设计流水线，可参考 [Stitch 原型指南](stitch-prototype.html)。
