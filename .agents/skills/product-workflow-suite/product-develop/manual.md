# 开发执行与真实验证指南 ($product:develop)

`product-workflow-0.9.3`

当需求文档与开发计划均已通过对抗审查并由你明确批准后，正式进入编码实现阶段。`$product:develop` 负责按计划逐步编写代码、执行自动化测试命令并记录真实验证证据。

---

## 一、解决什么问题

在传统的 AI 辅助编程中，最常见的失控情况是“未理清需求就急于改代码”或“声称测试通过但实际没有运行”。

开发执行阶段通过两道硬门禁守住底线：
1. **未批不动代码**：必须确认需求文档与开发计划已经由人类批准（状态为 `Reviewed`），严禁跳过方案直接修改业务代码；
2. **新鲜真实证据原则**：测试命令必须在当前代码上真实执行，记录真实的终端回显与退出码（Exit Code 0），绝不允许使用历史记忆或口头推测。

> 💡 **底层验证机制：RED/GREEN 严密循环与终端证据采集**
> 
> 助手在推进任务时，遵循严谨的测试驱动与证据回填流程：
> 
> ```mermaid
> flowchart TD
>     Task["1. 读取开发计划中的单项 TASK"] --> RED["2. 先行补充/运行测试 (RED 确认断言失败)"]
>     RED --> Code["3. 编写最小可用业务代码"]
>     Code --> GREEN["4. 重新运行本地测试 (GREEN 验证通过，Exit 0)"]
>     GREEN --> LogFill["5. 捕获真实终端回显写入 develop.md"]
>     LogFill --> Next{"是否还有后续任务"}
>     Next -- "继续" --> Task
>     Next -- "全部完成" --> WrapWait["6. 等待人工核验日志与收工确认"]
> ```
> 
> - **真实性硬门禁**：`develop.md` 记录的测试日志必须包含完整的时间戳、测试套件通过数量与退出码 0，严禁捏造假数据。

---

## 二、怎么对助手开口

当准备好开始编码时，直接对助手开口：

```text
需求和开发计划我都看过了，批准通过，开始执行编码和验证。
```

或者使用技能指令：

```text
$product:develop
```

如果开发任务较为独立，也可以指定推进模式：

```text
$product:develop --mode=single
```

---

## 三、开发推进流程与验证机制

助手会对照已批准的 `development-plan.md` 中的 `TASK` 清单逐步推进：

1. **计划一致性核对**：
   在动代码前，助手先核对当前代码分支与计划任务主题是否一致，防止改偏。
2. **遵守设计上下文规范**：
   若项目前端存在 `DESIGN.md`，开发时严格复用既有的色彩、间距规范与组件库，不在业务代码中自造视觉体系。
3. **逐项实施与测试验证**：
   每完成一个任务，立即在本地终端执行该任务绑定的测试命令（如 `npm test` 或 `pytest`），捕获实际退出码和终端输出。
4. **回填执行证据**：
   将实际修改的文件路径、测试运行日志和测试结果逐一写入 `develop.md`。

---

## 四、关键产物：`develop.md`

执行过程中，助手会在需求切片目录下生成并持续维护 `develop.md`。

> 📌 **关键产物：开发执行记录 (`develop.md`)**
> 文档包含以下关键部分：
> - **修改文件清单**：精确到本次改动的每一个源文件和配置文件路径；
> - **测试命令与真实输出**：记录执行的具体命令、终端输出截取以及退出码（`Exit Code: 0` 为通过）；
> - **未决风险与回滚方案**：若改动涉及配置变更或数据结构调整，记录上线注意事项与回滚步骤。

---

## 五、在轻量与完整工作流中的差异

- **轻量工作流 (Lite)**：短开发计划作为执行拆解合并在开发过程中推进，测试通过后直接进入收尾把关；
- **完整工作流 (Full)**：必须在开发计划获得正式 `Reviewed` 批准后才能进入本阶段，编码完成后进入 [验收收尾指引](product-wrap-up.html) 收工闭环。
