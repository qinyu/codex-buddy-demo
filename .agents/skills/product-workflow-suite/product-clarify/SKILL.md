# 产品问题澄清

## 命令

```text
$product:clarify <需求>
```

## 公共契约

执行本 skill 时必须遵守 `../product-workflow/references/common-contracts.md`。先给判断与依据，再问会改变方案的问题。问题归属、材料冲突和允许材料的边界读公共契约同名节，不在这里另写一套。

## 项目初始化配置门禁

写澄清产物前，先按公共契约读取 `.product-workflow-config.json`（如存在）和 `docs/product-workflow/project-profile.md`（如存在）。如果配置存在，澄清阶段必须复用其中的项目阶段、交付目标、代码探查许可、仓库结构、知识库现状、原型偏好、测试/发布策略和 open questions，不得重复询问已经初始化确认的项目级问题。

澄清阶段必须继承 `workflow_policy.product_mode`、`clarification_style` 和 `mode_detection`。旧配置缺少 `product_mode` 时按公共契约视为 `unknown`。分析或草稿把模式标成未确认并继续；进入 PRD 前才用一个问题确认模式，或请求用户授权按假设继续。不得因为配置缺字段而重新问一整组项目级问题。

配置缺失时，分析或已有材料的草稿按公共契约继续，不先询问 `$product:setup`。单独澄清要建立可复用项目配置时，可以询问是否运行 `$product:setup`（`$product:init` 是别名，仍认），或取得明确授权按本次假设继续。要进入完整 `$product:workflow` 时，必须先跑 `$product:setup`。如果配置的 `workflow_policy.code_exploration` 为 `user_declined`，本阶段不得静默搜索或读取代码。

## lite 推荐

用户要开工并进入正式产物时，第一轮轻量探查若确认是单按钮、单字段、单接口或单规则小改，影响不超过一个模块且预计一天内完成，应明确推荐轻量（`lite`）并说明依据，再只问用户是否确认。只要分析或草稿时不推荐档位，也不问是否确认轻量。与项目是新是旧无关（`product_mode` 不参与 lite 判定）。涉及新权限、敏感数据、schema/迁移、跨仓契约、架构边界或高风险发布时不得推荐 lite。用户确认后把 `run_mode` 写入 state，不生成 `clarify.md`，直接按 `run-mode.md` 写短 PRD；state 将 clarify 标为带原因的 `Not Applicable`。state 已有 `run_mode` 时只读沿用，不重推；用户说「走完整」时不得再劝 lite。

## 目标

full 模式在写 PRD 前澄清产品问题，沉淀目标用户、用户任务、场景、约束、风险、成功指标、非目标和待确认问题。

## 输入

需要一个具体需求或业务问题。用户要分析或草稿时，先给判断与依据。分析先写判断、依据和建议，再问会改变提出方向的那一个业务决定；缺目标用户、触发场景或成功指标且不影响这个方向时写入待决。用户明确只要分析、不要提问时，这次不问。

使用用户消息、提供的链接、仓库文件、现有产物等上下文。必须区分已确认事实和假设。有效稿、必要图和未读材料按公共契约 § 有效输入与缺失信息处理核对，记录在本阶段产物中。

## AI 不确定性澄清门禁

澄清阶段的目标不是替用户猜完整产品定义。先识别 AI 无法可靠确认的问题。分析先写判断、依据和建议，再问会改变提出方向的那一个业务决定；其余项标成待决。用户明确只要分析、不要提问时，这次不问。

写正式产物前形成“不确定性队列”，区分当前必须确认的问题、可进入 PRD 但必须追踪的问题、以及非阻断假设。当前必须确认的问题不能只写进正式产物后继续推进 PRD。

不确定性队列必须按 `product_mode` 排序：

- `zero_to_one` 优先确认目标用户、核心痛点、触发场景、MVP 边界、验证指标。
- `one_to_n` 优先确认现有流程、影响范围、兼容性、数据和权限边界、回归风险。
- `unknown` 在分析或草稿中标为未确认；进入 PRD 前优先确认产品模式。若用户授权按假设继续，必须记录模式假设会影响哪些 PRD、原型、测试和技术方案判断。

询问用户时必须遵守单问题澄清协议：每轮只问不确定性队列中最高优先级的一个决策点。跨角色的技术查证按公共契约分组，不并成对当前用户的一串问题。问的必须是**决策**，不是能查的事实：仓库结构、现有命令、已有页面/接口、配置值和 git 历史先自己查；查得到就写进产物，不要问用户“现在有没有这个接口”。每个问题必须给出推荐答案和依据（现有代码、同类页面或风险更低的默认）。用户可以改推荐，但不能只抛问题。只有用户明确回答，或明确授权“先按假设继续”，才能继续写完整澄清产物。用户授权按假设继续时，必须把相关内容标为“阻断假设与后续确认”，不得写成已确认事实。

请求进入 PRD 前，必须再次列出所有未解决问题及其影响，并要求用户确认是否接受这些假设。`unknown` 或按假设继续只能生成 `Draft`；只有用户明确接受模式假设、风险、受影响范围，并明确允许本 Clarify 阶段按该假设批准为 `Reviewed`，才能标记为 `Reviewed`。

## 项目上下文使用门禁

代码探查门禁（含 `code_exploration` 为 `user_declined` 时的处理）见公共契约 § Project Init Config Gate。

如果需求涉及既有产品、仓库、工具、页面、API、CLI、业务流程或历史产物，写正式澄清产物前先探索允许访问的项目上下文。用户要求“不要看项目/不要看代码”，或 `code_exploration` 为 `user_declined` 时，只用允许材料，标明实现未核实。允许探查时，先确认项目根目录；如果当前产品工作流目录已有 `project-wiki.md`，先读取其仓库/包地图、Repo Wiki 状态矩阵、系统边界和待确认问题，再提取 3-8 个关键词，用 `rg` 搜索相关文档、代码、脚本、测试、配置和历史产物，并在澄清产物中区分 Project Wiki 事实、repo wiki 导航事实、源码回查事实、假设和待确认问题。

**搜索证据要求（完成标准）**：本次允许并实际执行项目探索时，必须执行一次 `rg` 或等价搜索；只写“应执行”不算完成。输出或澄清产物必须记录：3-8 个关键词、实际命令、命中路径摘要（无命中也要明确记录）、由命中确认的事实，以及仍需用户确认的线索。权限、项目根目录或白名单不足以搜索时，分析或草稿写明证据缺口并继续独立范围；正式产物依赖该搜索结果时，先问用户补权限。不得用计划中的命令冒充已执行。

已有Wiki时按公共 Wiki Context Gate 读取相关导航与主题，页面存在且与任务有关才加载；缺页不强制生成。具体实现事实按源码探查许可回查，记录来源、冲突和未覆盖范围，不把Wiki当最终证据。

如果搜索为空、项目根目录不明确、或事实与用户表述冲突，分析或草稿标出假设和证据缺口；正式产物依赖该事实时，先问一个澄清问题。不得把假设写成事实。

## 输出

用户只要分析时，在回复里给判断、依据、建议和待决事项，不创建工作流目录、`clarify.md` 或看板。用户要求澄清产物时，创建或更新 `docs/product-development/YYYY-MM-DD-<topic>/`，把澄清结果写入该目录的 `clarify.md` 和 `.workflow-state.json`，并在生成 `prd.md` 前请求明确确认。只有用户已经给出一份有效交接路径时，才把这一份交接写到该路径。源头有更新就必须刷新看板 HTML：运行 `render_review_board.mjs`，确认 `.review-board/index.html` 存在。

澄清产物必须包含：

- 原始需求和业务背景
- 产品模式与澄清方式：当前 `product_mode`、`clarification_style`、`mode_detection`、模式来源、本阶段问题排序依据和仍未解决的模式假设
- 项目上下文事实和假设
- 目标用户和用户任务
- 当前流程和痛点
- 至少 3 个触发场景，除非该功能确实只有单一场景
- 目标、非目标、约束、假设、风险、成功指标、待确认问题
- 进入 PRD 前必须确认的评审清单

把可评审内容写入 `clarify.md`，状态只写 `.workflow-state.json`。AI 只写 `Draft`；`Reviewed` 等用户明确确认后再写。改过源头后运行 `render_review_board.mjs`。

本步骤不得写实现代码。用户已明确授权修复时，只准备修复范围、允许改动的项目接缝和待重验项，交给 `$product:develop`；不在澄清阶段改实现。

## 请求批准前自检

- 已执行公共契约中的批准前通用自检。
- Clarify：问题表格包含原始需求、事实、假设、风险、成功指标、待确认问题。
