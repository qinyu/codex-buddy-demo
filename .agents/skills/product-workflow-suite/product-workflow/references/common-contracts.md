# 产品工作流公共契约

各 `product-*` 阶段 skill 必须遵守本文件；阶段 `SKILL.md` 只保留阶段差异。`$product:workflow` 的 stage-gated / through-run 见 `run-mode.md`。

## 单一源头（skill 优化原则）

每类事实只允许一份可写源头。只更新那一份，所有展示必须跟着变。禁止把同一事实再抄进 HTML、另一份摘要或 agent 记忆。

| 事实 | 唯一源头 | 不是源头 |
|---|---|---|
| 阶段状态 / 当前阶段 | `.workflow-state.json` | 看板徽章、口头「已过」 |
| 澄清 / PRD / 用例 / 技术方案 / 计划 / 开工 / 开发记录 | 对应 `*.md` | 看板 HTML、聊天复述 |
| 给人看的简练层（评审要点、门禁、图） | **写在同一份阶段 Markdown 里**（如 `## 评审要点`、` ```mermaid `） | 生成器临时拼进 HTML 的第二份摘要 |
| 交互原型 | `prototype.html` 或 Stitch 记录 md | 评审看板 HTML |

简练层不是第二份文档：不要再写 `prd.review.md` 或只存在于 HTML 的「给人看」段落。要点和图必须进 `prd.md` / `clarify.md` 等源头；看板只渲染。

`.review-board/`（自包含的 `index.html`、`index.prev.html`、`history/`）和工作流根目录残留的 `index.html` **只是展示派生**。看板脚本与 mermaid 内联在 `index.html` 里，不另留旁路 js：

- 不得提交进 git（工作流目录 `.gitignore` 必须排除 `.review-board/` 与旧壳文件）
- 不得作为阅读上下文、知识库/代码索引、批准依据
- 发现 HTML 与 md/状态不一致时，以 md 和 `.workflow-state.json` 为准，改源头后重建或刷新看板，不要改 HTML

## 材料承接

按材料能支持的决定继续，不要求用户先选档位或补齐上游文件：零散反馈先形成问题判断；已有方案先审缺口；已确认规格直接接续交接、实现或验证；变更只处理受影响部分。同一任务可以几种成熟度并存。

先给判断与依据：基于现有证据写出问题判断、可行建议和关键取舍，再问会改变方案的问题。分析先写判断、依据和建议，再问会改变提出方向的那一个业务决定；不先发问卷，也不提前推荐轻量或写正式产物。用户明确只要分析、不要提问时，把该决定留在待决，这次不问。证据不足时给暂定判断和验证办法。有效决定直接复用，不把缺文件当成重新采访。

简短说明沿用哪些结论、本次补什么，并引用材料位置或版本。已决定、资料记载、实现核实、假设分开写。AI 纪要不是批准；纪要里的“达成一致”不自动成为批准记录。材料冲突时查原文或实际决定，逐字记录限制纪要结论，不按文件更新日期盲选。

用户拒绝读代码时只用用户允许的材料，继续不依赖源码的范围，并标明实现未核实。用户允许读取实现时，规则追踪使用提供材料和允许访问的实现；不把结论限制在本次消息附带的片段。

## 问题归属

能从允许材料查到的事实自己查。业务目标与业务规则由有权的业务方或 PM 决定。接口、取数和系统限制交给对应责任角色核实。每个未决项写清问题、影响、所需证据、责任角色和阻断范围。身份未知时写责任角色，不虚构负责人，也不反复要求当前 PM 回答其明确不知道的技术事实。

同一决策者只问会改变方案的最关键一项。跨系统查证按责任角色各列一小组问题，允许异步反馈。问题清单只是草案，不是已发送的消息，也不是已分派的任务；联系他人或创建任务按已有授权执行。只暂停依赖该答案的内容；能独立完成的判断继续。

## 存量增量

存量需求先从相关页面、文档或允许访问的实现确定要保留的入口、页面结构和既有业务规则，并写明本次增量。依据未到手时标待核实。“升级”“优化”不表示推倒重做导航或整套界面。此规则适用于所有原型工具与研发阶段。

局部变更只重审受影响的规格、原型、用例和批准；权限、编号和未改规则保留。不为缺一个文件名重建整条上游。缺旧字段不跳过有效门禁：`product_mode` 缺失、commit 变化或旧配置缺项，不取消适用的批准、验证和访问限制。

分析、草稿、单次评审交接或单阶段交付不因缺配置、模式未知、commit 变化或 `user_declined` 停下，也不因此改跑完整工作流、`$product:setup` 或 `$product:init`：用本次给出的事实继续评审交接，标出未核实项。完整 `$product:workflow` 仍先跑 `$product:setup`，显式完整档的组织门禁和未批准不实现保持不变。`unknown` 进入 PRD、原型、测试、技术方案或开发计划前，仍按单问题确认模式或取得按假设继续的授权。`code_exploration=user_declined` 时不读取源码、测试、配置实现或 CI。

## 交接变更

评审交接复用当前规格及其来源/版本，在既有产物里保留目标、关键业务规则与数据来源、保持不变的行为、未决项及责任角色、对应验收。小任务用一段摘要加原文引用，不另造完整交接文档。未核实的技术项标明责任角色。评审稿不授权实现、发布或对外发送。

接收方先简述理解和相对原材料的差异，再补技术事实。已有结论不重开访谈。复述理解是接续工作的一部分，不是再次批准的门槛。确需改变已定业务规则时，只提交该差异供决定。

切片引用同一规则及其验收，必要时保留跨任务的整体检查；沿用已有编号，不复制多份规则正文。收到变更或发现遗漏时，核对当前基线，说明变化、影响的产物/任务/用例、保持不变的内容和重新评审范围。只更新本次授权范围内的内容；范围外依赖记录影响与责任角色。

局部修订仅使受影响的批准和验证证据需要重新核对：只把受影响条目改回 `Draft` 并标 `revising`。不受影响条目的有效编号、规则、批准历史和条目级 `Reviewed` 标记保留。不清空全部成果或重跑全套阶段。显式组织批准缺失仍阻断依赖该批准的开工和实现；已确认且未变化的决定不重问。分析、草稿和评审交接不把缺批准当成停止条件。存在未授权的关键决定时保留可审阅差异，继续无关部分。

## 语义验证

只提供材料时，规则追踪只依据本次给出的片段、交接和测试记录下结论。最早可见缺口只说明这份材料，不写成整个项目的根因。用户允许读取实现时，同时核对允许访问的实现，不把已授权的查找排除在证据之外。数据来源、关联、权限和状态规则要单独检查业务语义；点击成功或接口返回成功不等于规则成立。验收要能区分正确实现和表面可用的错误实现。

例如“级联选项来自字典”：在允许的隔离测试数据中改变字典项，确认选项按约定刷新机制更新；改变上级项，确认下级过滤及旧值处理符合已定规则；无匹配时验证空状态。旧值处理未定时列明待决，不擅定清空或保留。原型的模拟数据不能证明真实接口接通；纯用例编写不修改数据。

规则已写但实现不符时，沿规格、交接/切片、实现、验证记录定位丢失点。只读检查在授权范围内先做。不凭一份会议反馈认定需求不清或研发失误。材料不全时给出已知事实、证据缺口与最短查证路径。

用户只要求检查时，交付符合项、偏差及证据、未验证项。只读检查不修改代码或业务数据，不声称已运行测试或已定位整仓根因。没有这句修复授权时，检查到的偏差也不改代码。

用户已明确要求修复时，按当前阶段交接，不在本段直接改代码。澄清只准备修复范围、允许改动的项目接缝和待重验项，交给 `$product:develop`。开工只做门禁和执行方式准备，不写实现。只有 `$product:develop` 在既有开工门禁通过后，才完成授权范围内的修复与重验。显式组织批准缺失仍停止开工和实现。

## 语言和产物

- 默认用简体中文回复用户，并用简体中文编写产品工作流产物和评审说明。看板 HTML 只展示这些源头，不另写一份 tab 正文。
- 命令名、文件路径、API 路径、代码标识符、枚举值、测试编号、验收标准编号、验证命令保留原始技术形式。
- 技术展示写进行内代码或代码块：路径、命令、配置和代码保留原字符，不夹带为了展示新增的 Markdown 转义字符。语法所需的合法反斜杠（如正则、JSON、路径）不得删除；疑似转义污染但无原稿时保留原输入，索取原文件或代码块，不猜原配置。
- 本条只约束技术字符串：正文的强调、列表、编号和标点转义照常写，不因本条改写或删掉正常 Markdown 转义。
- 只有用户明确要求其他语言时，才使用其他语言。
- 仓库根目录若有 `AGENTS.md` 或 `CLAUDE.md`，每个 product 阶段开始时先读它。项目硬规则以章程为准，本文件和各 SKILL 不重复抄写。

## 有效输入与缺失信息处理

澄清、PRD 或修订需求前，确认本轮有效版本：需求 owner 点名的确认稿为业务输入，原修订稿只供追溯。版本不明或内容冲突时按现有单问题澄清协议确认，不替 owner 接受全部修订或决定哪份过期。Word 等材料优先由 owner 提供清洁最终稿或 Markdown；导出后仍需核对删除内容是否残留，转换格式不是确认内容。

把材料与影响记录在现有阶段产物中，不新建重复清单：哪些已读、哪些未读、支持什么结论、缺失影响哪些范围或验收。用户给出的图/原型先核访问能力及用途，再直接读取相关内容；不以另一模型的二次描述冒充已读原图，不绕过加密或权限。

- **必要业务图**：缺失会改变字段、交互、权限、范围或验收时，不把相关结论写为已确认，也不推进依赖它的阶段批准；请 owner 提供授权替代材料或确认具体假设。
- **非阻断参考**：装饰/样式参考缺失但不影响当前范围时，标未读及影响，继续独立不受影响的工作。不得因任一图片打不开就停掉所有工作。
- **旧 PRD 已污染**：取得新输入后复核受影响的 PRD/原型/用例及其下游，按既有修订与批准流程处理，不将旧内容直接沿用或整份无依据重写。

不把删除线解析、通用转换器、额外输入文档或“所有图读完”新增为开工门禁；能提供确认稿时优先使用简单输入方式。

## 认切片（当前工作流目录）

一条需求 = 一个切片目录（`docs/product-development/YYYY-MM-DD-<topic>/`），内含各阶段产物、`.workflow-state.json`，选用门户时还有 `.limix-artifacts.json`。正式阶段产物写在这个目录。只有用户已经给出一份有效交接路径时，才把这一份交接写到该路径；这不把全套产物改成可选，也不另开第二套目录。独立阶段命令（直接点 `$product:prd` 等）先钉住切片再读写，不靠会话记忆。分析、草稿、评审交接和只读规则追踪不先认切片，也不因多个切片停下。

认切片按这个顺序，命中就停：用户给出的路径 → 当前目录自己就是切片 → `docs/product-development/` 下恰好一个切片 → 否则列出路径问用户。不要用最近日期。多切片时不猜；问清楚之前不写本阶段产物。列出多个候选时，仍按单问题澄清协议给出互斥选项；只有用户指令或已核实仓库事实提供了与日期无关的依据时，才推荐某个候选，并说明依据。没有这类依据时，请用户点名选择，不挑选任何候选；日期、新近度和目录排序都不是推荐依据。

钉住切片后查前置状态：适用前置阶段为 `Draft` 或缺文件时停下来，请人完成/批准，或由用户明确「本切片跳过」并写入带原因的 `Not Applicable`；`run_mode=lite` 时被裁阶段不要求文件。跳步不跳产物和批准。用户说「就当新需求」时新建切片目录与新 state，不接入旧切片。

## 续跑与无效循环处置

换会话或中断后继续时，按顺序取事实：§ 认切片 定位切片 → 读 `.workflow-state.json` 的阶段状态与 `slice_plan` → 读现有计划、产物和上一轮验证证据。依据是这些落盘事实，不是会话记忆，也不另建聊天账本或续跑清单。

- **接下一项**：只续接未完成的真实任务（适用阶段里状态不是 `Reviewed`/`Not Applicable` 的最早一项，或计划里未完成的 `TASK-xxx`）；已批准阶段不重做，已有新鲜证据不重跑，仅限目标内容未变且满足该阶段时效要求。开发/收尾要求本轮执行的验证仍须执行；批准稿回改或证据过期时走既有修订/验证流程。
- **状态与产物冲突**：state 与文件对不上时（如状态 `Reviewed` 但文件缺失、有 Git 且要求提交的任务标 done 但没有合格提交），报告差异并交回既有批准流程处理，不自动改绿、不替人改状态、不把重做当成修正。
- **重复失败**：同一动作在没有新信息（新输入、新证据、新的失败原因）的情况下反复失败时，停止重试，汇报已试动作与实际结果，给出恢复选项（回滚到上个已知好点、改走另一条路径、请人处置），不硬闯也不假报通过。
- **等待中的合法长任务**：构建、评测、审批等仍在推进的等待不判停滞；不设统一的耗时或次数阈值，判定依据是任务是否仍可能推进、有没有新证据。

## 共享合同事实源与变更影响

跨前后端或多个功能共用的接口、数据结构、事件合同，复用项目已有的事实源：仓库里的 OpenAPI/schema/类型定义、repo wiki `contracts.md`、已批准技术方案的 API 表。Wiki 导航和方案描述须回查对应实现/契约版本；多处不一致时列差异交 owner 确认，不凭列举顺序决定权威。不在切片里另造第二份接口事实源，也不为此新建数据目录、fixture 目录或审批系统。

变更共享合同前，先识别并写进本阶段产物：现有调用方（前端、后端、任务、测试分别谁在用）、兼容性影响（字段增删、语义变化是否破坏消费方）、验证范围（要重跑哪些受影响消费者的测试与回归命令）。

事实源缺失或没有 owner 时，把缺口列为待确认交回人处理；吃不准的部分不写成已确认，独立不受影响的范围继续推进。合同变更仍走既有批准与测试流程，不新增状态字段、审批角色或必填产物。

## Project Init Config Gate

> 本节定义读配置、配置强度、stale/不可读处理、`product_mode` 缺失、`code_exploration` 为 `user_declined` 等全部通用规则。各阶段 `SKILL.md` 的「项目初始化配置门禁」章节只列阶段独有的 `workflow_policy.<键>` 逻辑（例如 prototype_route、test_automation、project_wiki），其余读配置、stale、explicit_override、user_declined 规则一律继承本节，不必逐字复制。

进入正式阶段并使用项目事实、仓库事实、设计路线、测试策略或实现门禁前，必须先检查活跃项目根目录的 `.product-workflow-config.json`。分析、草稿、评审交接和只读规则追踪不因缺配置、配置刷新或未知模式停下。如果存在，必须读取并遵守其中的 `workflow_policy`；如果 `profile_path` 指向的 `docs/product-workflow/project-profile.md` 存在，必须在需要解释策略依据、open questions、freshness 或 override 时读取它。

配置强度为 `strong_with_explicit_override`：后续阶段默认必须遵守初始化配置。只有用户明确说明本次需求覆盖项目默认配置时，阶段才可偏离；偏离时必须在当前阶段产物中记录 `explicit_override`、覆盖原因、风险、受影响阶段和后续回收点。

如果 `.product-workflow-config.json` 缺失：

- 读取AGENTS.md中最小Setup记录的明确选择；缺配置本身不阻止分析、草稿、评审或只读追踪，不自动运行Setup。
- 用户选择完整配置时请用户执行 `$product:setup`；正式阶段检查实际需要的事实和批准，缺信息只请求相关决定，不把未知当同意。

如果 `.product-workflow-config.json` 不可读、不可解析、`schema_version` 不支持，或 `project_root` 与当前项目根冲突，不得猜测配置；必须请求 `$product:setup --refresh`，或请求用户明确授权继续且记录风险。

freshness 的权威判断只比较当前项目根 `git rev-parse HEAD` 与 profile/config 记录的 `freshness.git_commit`；旧配置的关键文件指纹只作兼容参考，不参与过期判定。commit 变化时建议 `$product:setup --refresh`（直接跑 `$product:setup` 默认也是增量 refresh），不是硬阻断；用户明确继续时，当前阶段产物必须记录 stale-config continuation 和额外源码/配置回查责任。

如果 `.product-workflow-config.json` 存在但 `workflow_policy.product_mode` 缺失，必须视为 `unknown`，不得报错或猜测为某个模式。`unknown` 不阻断 `$product:setup --refresh`、项目初始化、信息收集或 Project Wiki 探索；但完成配置批准，或进入 `$product:workflow`、PRD、原型、测试、技术方案、开发计划等正式下游阶段前，必须按单问题澄清协议确认模式，或取得用户明确授权按假设继续并记录风险。

如果 `workflow_policy.code_exploration` 为 `user_declined`，任何阶段不得静默探查源码、测试、配置或 CI；只能使用用户提供信息、已有 profile/config、已有产品产物和用户允许的文档。需要查代码时必须先请求用户修改该配置或提供本次明确授权。

## UI 栈参考门禁

涉及界面、交互、前端测试或 UI 实现时先按目标文件/配置识别栈，只加载一份对应参考：

- Vue：`references/stacks/vue.md`
- WPF：`references/stacks/wpf-ui.md`
- 小程序：`references/stacks/miniprogram.md`

多端需求按端分别读取，不把 Web、XAML、小程序 API 或测试写法混用。参考文件只补端侧边界；版本、命令、框架和组件仍以目标仓实际文件为准。

## Wiki Context Gate

正式阶段在使用项目或仓库事实前，必须先执行本门禁；阶段 `SKILL.md` 可以补充阶段专属页面，但不得绕过本门禁。分析、草稿、评审交接和只读规则追踪不运行 Wiki 或 code-wiki 门禁，不生成或刷新 Wiki。

### 读取与路由

按相关主题读取已有单仓docs/repo-wiki/、跨仓docs/project-wiki/和切片project-wiki.md；旧repo-wikis/*.md保留读取。已有导航指针优先，不搬目录，不为新切片复制知识树。catalogue/status/shared-language存在则按需读，缺失时不能声称新鲜度或术语已经验证。

跨仓问题先核对仓库/部署边界与来源。缺路由可以用授权材料确认，不自动生成Wiki。证据不足只阻断受影响结论，请求材料或授权。用户拒绝建Wiki不等于拒绝源码探查；user_declined时不读源码或代码图，仅用授权材料。

### 事实核对

涉及接口、权限、数据、UI行为、测试命令或部署等实现事实时，在许可内回查源码/测试/配置。Wiki是导航，不是最终事实。记录已读页面、回查路径、冲突、未知和假设。commit变化仅提示复查相关区域，不自动清空整套批准。

需要代码图证据时调用wiki内部代码分析。detect_code_wiki.mjs的query_ready表示有图、有Wiki且政策允许尝试，不保证调用成功或索引新鲜。detected但不可查询先说明原因；未命中/not_applicable按授权材料继续，不安装或建空图。search/cite/impact语义保留，MCP或shell均可。

### 创建与维护

知识生成/更新唯一归wiki，通过Skill调用，不跨目录深链。Setup负责选择；后续按明确选择补相关缺口；Wrap-up按实际变更调用update。缺Wiki时仍可读已有材料，所选知识写任务报告缺依赖，不复制备用流程。

旧workflow_policy.project_wiki的required/optional/not_applicable、repo_wiki的prefer_existing_or_generate_missing/prefer_existing_only/not_applicable继续读取。required是旧批准，改变须explicit_override；新默认可选。旧state字段和批准证据保留，不因为skill入口删除而改写枚举或重置状态。

计划和未实现方案不写成现状；实现偏离批准约定先报告并裁决，不通过改Wiki掩盖。政策或章程需要变化时请用户执行Setup refresh，而不是由Wrap-up调用人触发Setup。

### 自动化测试上下文

automation-test-plan.md仍是测试与实现之间的共享证据；涉及实现、UI/API、权限/数据和跨仓回归时按现有门禁读取。Not Applicable继承其理由，不另造测试范围。

## 贯穿式不懂就问门禁

> 公共契约统一自主完成、澄清与授权；阶段 Skill 只列独有的阻断项。单问题澄清协议 → 不确定性队列排序 → 按假设继续授权 → 请求批准前附清单。用户当前指令与项目章程优先。

- 先完成当前授权范围内可做的工作，自检并修正后交付。能从现有材料与允许读取的环境查到的事实先查；不把可解决的疑点、缺少可选工具或不影响本阶段的风险变成全流程停止。局部产物只做局部，不为凑固定条目或阶段生成无关文件。保留已有实现，按本次风险验证，不为补可选报告/Hook 自动安装基建。
- 遇到关键业务决定、相互冲突的事实、验收不可判定、权限/敏感操作、明确评审门禁或当前阶段确实依赖但无法取得的证据，停在该决策或依赖处。先修能修的前序事实，再问人；不得猜测批准、绕过开工、擅自探查被拒绝的源码或执行未授权的外部操作。其他可独立交付的草稿可继续，标明尚未核验与阻断范围。
- 询问用户必须遵守单问题澄清协议：每轮只提出一个需要用户作答的决策点。一个问题必须带必要上下文、**推荐答案（含依据）**和 2-4 个互斥选项；用户可以改推荐，但不能只抛问题。不得把多个互相独立的决策塞进同一轮。
- 能从仓库、配置、已有产物、git、命令或公开文档查到的事实，不得拿来问用户。先查；查不到或互相冲突时，才把冲突本身当成决策点来问。
- 如果当前阶段存在多个阻断问题，必须先建立不确定性队列，按对范围、验收、权限/数据、架构/API、发布/回滚和验证可执行性的影响排序；每轮只问最高优先级的一项。用户回答后，再根据剩余队列继续问下一项。
- 非阻断性不确定项可以标为假设或待确认问题，但不得静默省略；请求阶段批准时必须附上未解决不确定项清单。只有真正挡住当前目标的项才进入阻断队列，不能把所有 concern 当 blocker。
- 对关键业务假设，只有用户明确回答，或明确授权“先按假设继续”并接受对应风险，才能据此推进受影响内容。授权按假设继续时，必须在产物和评审请求中列出具体假设、影响范围、受影响编号和后续回收点；不得写成已确认事实。低风险可逆的表达假设可标注后形成 Draft，不据此请求批准。

## 产品模式协议

所有 product workflow 阶段必须识别并继承 `workflow_policy.product_mode`：

- `zero_to_one`：从 0 到 1，强调价值假设、目标用户、核心痛点、MVP 边界、原型验证、成功指标和学习闭环。
- `one_to_n`：从 1 到 n，强调现有系统事实、增量范围、兼容性、迁移路径、权限和数据边界、回归风险、发布与回滚。
- `unknown`：模式尚未确认。允许继续做项目初始化、信息收集、Project Wiki 探索，或在用户授权下按假设生成草稿；不得把 PRD、原型、测试、技术方案或开发计划标记为 `Reviewed`，除非用户明确接受模式假设、风险、受影响范围，并允许本阶段按该假设批准。

模式判断采用混合策略：

1. 用户显式指定优先，例如“这是从 0 到 1”“这是现有产品迭代”“按 1 到 n 做”。
2. 用户没有指定时，agent 根据项目阶段、是否已有生产系统、是否存在既有代码/用户/流程/配置、需求是否以新增还是改造为主进行推断。
3. 推断后必须用一个问题向用户确认，除非用户已经显式指定。
4. 用户可以通过自然语言或命令参数覆盖推断结果；如果用户表述和项目证据冲突，必须只问一个冲突确认问题，不得直接覆盖用户。

阶段产物在阅读上下文、项目上下文或等价章节中必须记录当前 `product_mode`、模式来源、采用依据、本阶段因此调整的范围/验收/技术约束，以及 `unknown` 或按假设继续时的风险。

阶段完成标准：

1. 写入本阶段源头文件，并把该阶段状态写入 `.workflow-state.json`（AI 只写 `Draft` / `Blocked` / `Not Applicable`）。
2. 图和评审要点写在同一份源头文件里，用 mermaid 围栏；不要为填 tab 去改 HTML。

## 制品账与门户同步

制品账是派生的：阶段审批读 `.workflow-state.json`；本地提交读 git；规格开工在选用门户且已绑定时读门户，否则读套件开工记录。

`portal_sync=off`（缺省；旧值 `manual_only` 同）时只维护本地制品账。完成标准：不调用 `limix`；不创建、不写入 `.limix-artifacts.json` 或 `.product-workflow-portal.json`；不声称已同步门户。开工仍做下面 § 开工前交付物核对的状态检查，以及有 `.git` 时的本地提交检查。开工时间写在 `start-implement.md`（lite 写进 `develop.md`），不另开门户文件。

`bound_project` 时，阶段只调用 `scripts/portal-handoff.mjs` 的 `portalHandoff`。缺来源或条件写传输时返回未同步；具备传输时返回该入口的实际结果。`synced` 只表示回读一致，不是人工批准。阶段正文不拼 `limix`、不描述整套提交、冲突裁决或 §(e) 上报。阶段写成 Draft 或 Reviewed **不是**自动上传，也不是门户确认。

## 开工前交付物核对

进入 `$product:kickoff` / `$product:develop` 之前跑。lite 在 develop 内联合并时同样跑。过不了就停，不推荐执行方式、不写生产代码。

**1. 状态**

按 `run-mode.md`：lite 短 `prd.md` 必须 `Reviewed`，短计划允许 `Draft`；full 必填 `prd.md` 与 `development-plan.md` 为 `Reviewed`，其余方法产物 `Reviewed` 或带原因的 `Not Applicable`。任一适用阶段仍是 `Draft` / `Blocked` / 缺文件，或带 `revising`，停下来请人批或回前序阶段。

**2. 本地提交（切片在 git 工作树里才查）**

对每个状态为 `Reviewed` 的源头文件（上表，不含看板 HTML、`.workflow-state.json`）：

```bash
git status --short -- <源头文件>
git log -1 --oneline -- <源头文件>
```

未跟踪、已修改未提交、或根本没有 commit：列出文件，停下来请人提交。看板、state、门户绑定文件按 ignore 不要求进仓。没有 `.git` 时跳过本步。已 commit、未 push：警告别人拉不下来，不挡开工。

**3. 门户（仅 `portal_sync=bound_project`）**

本地开工硬卡（§1 状态、§2 本地提交）通过后，只调用 `portalHandoff`。返回 `unsynced` 时记下未同步，不拼门户命令，不阻断 `$product:develop`。`portal_sync=off` 时 `portalHandoff` 零门户调用并跳过整段：不跑同步，不因缺少门户文件而停。

## 状态转移规则

用户授权“写稿/审查”可完成草稿；“按此方案实现”仅在未变的约定范围内有效。不要求用户用同一句话重复授权，但它不代替 `Reviewed` 人工批准、门户确认开工或新权限。用户明确要逐阶段评审时照做；授权连续生成草稿时，不因每个 Draft 停下重问。门户离线只报告同步受阻，本地产物与门户批准分开；绑定门户不再阻断本地开工。

权威表述见 `product-workflow-suite/product-setup/references/charter-rules.md` § 状态转移（含操作细则与来源）；本节只列套件执行口径，不重复展开：

- 阶段状态枚举：`Draft` / `Reviewed` / `Blocked` / `Not Generated` / `Not Applicable`。
- AI 只能写 `Draft` / `Blocked` / `Not Applicable`（含 `Not Generated`）；`Reviewed` 是**人专用**状态，只有用户明确批准后才能写入。
- 已批准产物（`Reviewed`）再次修改时：状态回 `Draft`，并在 `.workflow-state.json` 该阶段对象上加 `"revising": true`（看板据此渲染「已回改待复审」徽章）；复审通过后写回 `Reviewed` 并移除 `revising`。
- 写完 state 后运行 `node product-workflow-suite/product-workflow/scripts/validate_workflow_state.mjs <工作流目录>`。枚举、`current_stage`、`run_mode`、`revising` 只挂 `Draft` 这些规则由脚本判定；报错就先修 state。`render_review_board.mjs` 遇到校验错误不出壳。写 `Reviewed` 时带 `reviewed_by` 与 `reviewed_at`。
- 用户明确豁免测试基建或 Git Hook 后，在 state 顶层 `waivers[]` 写 `{ "task": "TASK-000", "owner": "...", "reason": "...", "waived_at": "ISO-8601", "stage": "start-implement" }`；`stage` 可省略，省略时看板在开工与开发执行两处显示。豁免徽章固定写「已豁免 · 未完成」，不得把对应任务或测试状态改绿。

## 批准前通用自检

- 正文、评审说明、图表说明默认使用简体中文。
- 给人看的文字要好懂：先说结论，再用证据；同等元素字数接近、句式一致；换行不要留下一两个字的孤行。
- 产物开头说明本阶段为什么存在、谁来评审、评审人要做什么决定、依赖哪些前置事实或假设。
- 表格、图示或矩阵配有中文解释，说明它帮助评审什么。
- 产物足够厚，不依赖评审人要求“展开一下”。
- 编号和结论能被下游步骤引用。
- 请求批准时列出仍未解决的不确定项；用户未确认接受前，不得把阶段状态写成 `Reviewed`。
- 已遵守状态转移规则：AI 只写 `Draft`/`Blocked`/`Not Applicable`；已批准产物被本阶段回改的，已降回 `Draft` 并在该阶段对象上标 `revising: true`。
- 已记录本阶段采用的 `product_mode`；如果为 `unknown`，已说明仅允许草稿继续，或已记录用户明确允许按已接受假设批准为 `Reviewed` 的依据、风险和受影响范围。
- 不得使用未决占位词、空泛验证词或笼统边界处理表达作为正式内容。
- 本阶段改过源头文件或 `.workflow-state.json` 的，已运行 `render_review_board.mjs`，且 `.review-board/index.html` 存在。用户明确说无需新建看板且看板原本不存在时，不新建看板，并运行 `prepare_prototype.mjs --no-board`；已有看板时只刷新。该条不免除完整工作流的必需记录和批准。
