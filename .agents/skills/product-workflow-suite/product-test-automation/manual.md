# 自动化测试方案指南 ($product:test-automation)

`product-workflow-0.9.3`

当需求涉及关键业务主链路、复杂的跨系统接口或高频回归场景时，仅仅依靠单元测试往往不够。自动化测试方案技能负责规划单元测试之上的端到端（E2E）、接口契约与集成自动化测试策略。

---

## 一、解决什么问题

在核心系统迭代中：
- 单元测试无法完全覆盖分布式服务调用、真实数据库交互与第三方支付网关网络行为；
- 缺乏自动化的端到端回归方案，每次发版都需要测试人员大量手工重复点选；
- 自动化测试脚本往往分散在不同目录，没有统一的测试范围、测试环境要求与数据准备说明。

`$product:test-automation` 在正式开发前，根据业务用例和技术方案梳理出一份结构化的自动化测试方案，明确哪些场景用自动化守护、哪些命令用于回归。

> 💡 **底层架构分层：测试金字塔与自动化回归策略**
> 
> 工业级自动化测试体系采用分层守护策略，避免所有场景都堆在脆弱的端到端 UI 层：
> 1. **底层单测 (Unit Tests)**：覆盖纯函数计算、算法与边界分支，运行极快（毫秒级）；
> 2. **中层接口集成 (API / Integration)**：覆盖真实数据库交互、跨模块 RPC 路由与网关鉴权；
> 3. **顶层端到端 (E2E / Scenario)**：覆盖核心用户旅程，通过无头浏览器模拟真实用户点击。
> 
> ```mermaid
> flowchart TD
>     E2E["顶层：E2E 端到端场景测试 (覆盖核心用户主旅程)"]
>     API["中层：API 接口与契约集成测试 (覆盖跨服务通信与数据流)"]
>     Unit["底层：单元测试 (覆盖纯计算、分支逻辑与单测门禁)"]
>     E2E --> API --> Unit
> ```

## 二、怎么对助手开口

用自然的工程语言向助手提出诉求：

```text
为当前切片梳理一份自动化测试方案，重点覆盖支付回调与退款冲正的接口集成自动化。
```

或者指定测试层级与工具框架：

```text
按已有的 Playwright 环境，为结算流程的新交互规划 E2E 自动化测试用例与环境前置要求。
```

## 三、适用条件与自动裁剪规则

并非所有需求都需要出具单独的自动化测试方案，工作流同样遵循客观裁量：

| 业务场景 | 是否适用 | 处理方式与状态 |
|---|---|---|
| **新增核心支付/交易流程、高频 API 变动、跨端集成** | **适用** | 生成 `automation-test-plan.md`，状态初始为 `Draft`，人工审阅通过后流转为 `Reviewed`。 |
| **单模块内部重构、展示型页面调整、无新自动化范围** | **不适用** | 系统自动在状态机中标记为 `Not Applicable` 并写明原因，不产生冗余文件。 |
| **轻量工作流 (Lite)** | **默认裁剪** | 自动标记为 `Not Applicable`。 |

---

## 四、关键产物：`automation-test-plan.md`

产物生成在需求切片目录下：`docs/product-development/YYYY-MM-DD-<需求名称>/automation-test-plan.md`。

> 📌 **关键产物内容**
> - **自动化测试范围矩阵**：明确划分单元测试、集成测试与端到端测试的分工与层级；
> - **环境依赖与测试数据准备**：运行测试所需的 Mock 服务、测试数据库种子与密钥准备；
> - **CI/CD 触发策略**：哪些测试在本地提交时跑，哪些测试在合并请求（MR）或夜间流水线中跑。
