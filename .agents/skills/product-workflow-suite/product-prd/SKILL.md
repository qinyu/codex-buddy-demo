# 产品 PRD

## 命令

```text
$product:prd
```

## 前置条件

使用当前产品工作流目录。如果缺少澄清上下文，先询问需求并运行澄清步骤。跨仓/包/部署需求按公共Wiki Context Gate核对边界与证据；已有资料直接引用，缺Wiki不强制生成。

## 公共契约

执行本 skill 时必须遵守 `../product-workflow/references/common-contracts.md`。

## 输入

读取问题澄清、`project-wiki.md`（如存在）、`.workflow-state.json`、用户提供的链接/文档和用户决策。按公共契约 § 有效输入与缺失信息处理复核有效稿、必要图与未读影响；澄清之后的新输入不能静默覆盖已批范围。如果目标用户、成功指标、范围边界、仓库职责或系统边界不清楚，先问一个澄清问题，不要写薄 PRD。

写 PRD 前必须读取并记录 `workflow_policy.product_mode`。如果旧配置缺少该字段，按公共契约视为 `unknown`，必须先用一个问题确认模式，或取得用户明确授权按假设继续。`unknown` 模式下不得把 PRD 标记为 `Reviewed`，除非用户明确接受模式假设、风险、受影响范围，并明确允许本 PRD 阶段按该假设批准为 `Reviewed`。

## AI 不确定性澄清门禁

写 `prd.md` 前，先列出 AI 无法可靠确认的产品问题，并判断是否阻断 PRD。阻断性不确定项不得仅写为“假设”或“待确认问题”后继续产出完整 PRD。

PRD 开始前必须生成“不确定性清单”，逐项写明来源、影响范围、是否阻断当前 PRD、是否会阻断原型/测试/技术方案/开发计划。当前 PRD 阻断项必须先问清楚；不得只解决一个明显问题，然后把其他会改变用户旅程、验收标准或范围的未知项带入完整 PRD。

以下情况必须先问用户，再写或重写 PRD：

- 目标用户、核心场景、业务目标、成功指标、范围边界或非目标不明确。
- 用户旅程、用户故事、验收标准、优先级需要靠 AI 猜测才能成立。
- 权限、安全、隐私、合规、数据保留、审计、计费或运营策略会影响验收。
- 项目探索发现与用户输入、问题澄清或既有产物冲突。
- 待确认问题会改变超过 20% 的范围、验收标准或关键流程。

澄清时必须遵守单问题澄清协议。先建立 PRD 不确定性队列，逐项写明来源、影响范围、是否阻断当前 PRD、是否会阻断原型/测试/技术方案/开发计划；每轮只问最高优先级的一个阻断决策。用户授权按假设继续时，PRD 必须把这些假设集中放在“阻断假设与后续确认”中，并避免写成已批准事实。

请求批准 PRD 时必须附上仍未解决的不确定项清单，说明它们会影响哪些 `J/US/AC` 或后续阶段；用户未确认接受前，不得把 PRD 状态写成 `Reviewed`。

## 项目上下文探索门禁

写 PRD 前必须探索当前项目/仓库上下文，不得只依赖澄清产物和用户口头决策。除非用户明确要求“不要看代码/不要探索项目”，否则必须执行：

1. 确认当前产品工作流目录和活跃项目根目录。
2. 判断仓库、包和部署边界，复用已有知识入口；缺Wiki用授权材料核对，不强制生成。PRD引用实际证据，知识缺口明确记录。
已有Wiki时按公共 Wiki Context Gate 读取相关导航与主题，页面存在且与任务有关才加载；缺页不强制生成。具体实现事实按源码探查许可回查，记录来源、冲突和未覆盖范围，不把Wiki当最终证据。
4. 从澄清产物、`project-wiki.md` 和 repo wiki 页面提取 3-8 个关键词，使用 `rg` 搜索相关代码、文档、脚本、测试、配置和历史产物。关键词应覆盖业务名、功能名、技术对象、命令/API/状态名及同义词。
5. 阅读最相关的文件片段，区分：
   - 已存在能力、可复用模块或脚本
   - 已知限制、安全要求、权限/审计/测试约束
   - 与澄清假设冲突或需要用户决策的事实
6. 在 `prd.md` 中写入“项目上下文探索”或等价章节，列出探索过的关键文件/目录、`project-wiki.md` 中继承的事实、已读 repo wiki 页面、已回查源码路径、得到的新事实、PRD 如何受这些事实影响，以及 repo wiki 缺口或过期风险。不能只说“已探索”。
7. 如果搜索结果为空、项目根目录不明确、Project Wiki/repo wiki 与代码探索冲突、或探索发现与澄清结论冲突，先问一个澄清问题，不得直接写完整 PRD。

示例搜索方式：

```bash
rg -n "CLI|cli|命令行|doctor|workspace|product-workflow|render|validate|token|audit" .
rg --files | rg "(cli|workflow|doctor|workspace|token|audit|scripts|docs)"
```

探索范围要和需求相关，避免无差别读取全仓库。使用探索结果修正 PRD 的背景、当前流程、范围、非目标、验收标准、风险和待确认问题。

## lite 短 PRD

当 `.workflow-state.json` 的 `run_mode` 为 `lite` 时，不套用下方 full 厚度、5 条用户故事、8 条 AC、原型约束契约与图示要求。只写一个可直接决定是否开工的短 `prd.md`，且必须包含：

- `## 范围`：当前行为、小改位置、允许修改的模块/文件。
- `## 验收`：至少一个稳定 `AC-xxx`，写成可判定结果。
- `## 验证`：自动化测试或替代验证命令、执行位置、通过标准。
- `## 不做`：明确非目标和不扩大的边界。
- test-automation / technical-solution 等裁剪原因；初始化配置要求自动化测试时，同时记录本次 `explicit_override`、风险与回收点。

用户批准短 PRD 后才进入短开发计划。其余被裁剪阶段在 state 标 `Not Applicable` 并写原因，不生成空壳文件。

## 输出

full 模式下，写入或修订 `prd.md`，包含问题陈述、目标用户、目标、非目标、范围、用户故事、验收标准、约束、假设、风险和成功指标。

PRD 必须包含：

- 阅读上下文：说明为什么写这份 PRD、谁来评审、评审要做哪些决定、依赖哪些澄清事实和假设
- 产品模式：当前 `product_mode`、`mode_detection`、`clarification_style`、模式来源、判断依据、模式对 PRD 范围和验收的影响
- `zero_to_one` 模式下的价值假设、MVP 边界、可验证实验、原型验证方式、成功指标和学习闭环
- `one_to_n` 模式下的当前系统事实、增量变更范围、迁移/兼容要求、权限/审计要求、回归验收、发布与回滚要求
- 项目上下文探索：说明探索了哪些相关文件/目录、继承了哪些 Project Wiki 事实、读取了哪些 repo wiki 页面、确认了哪些已有能力/限制、哪些内容仍是假设
- 业务背景和问题陈述
- 目标用户/用户画像及其任务
- 目标、非目标、范围内和范围外
- 当前流程和目标流程。存量需求写明数据来源、关联关系和保持不变的行为；接口未核实时标明责任角色，假设不写成实现事实。
- 验收要能检出硬编码。字典、过滤和空状态写进可观察验收；旧值处理未定时列明待决，不擅定清空或保留。
- 局部修订保留有效编号和未受影响的已有批准，只重核本次变化。
- 原型约束契约（UI/交互需求必填，非 UI 需求改为流程/状态/控制台约束契约）
- 普通产品需求至少 5 条用户故事
- 至少 8 条验收标准，并映射到用户故事或可衡量结果
- 用户旅程、用户故事、验收标准必须建立同一套追踪关系，产物中必须包含“旅程 → 用户故事 → 验收标准”矩阵
- 相关的数据、权限、运营、边界需求
- 成功指标和度量说明
- 风险、假设、依赖、待确认问题

## 原型约束契约

PRD 不只是描述“做什么”，还必须约束后续原型“怎么表达”。面向页面、流程、HTML 原型或交互稿的需求，`prd.md` 必须包含单独章节 `## 原型约束契约`。如果缺少足够信息，先问用户或从项目/设计系统探索中补证，不得把约束留给原型阶段脑补。

### 原型约束不确定性队列门禁

在把“原型约束契约”正式写入 `prd.md` 前，必须先建立 `原型约束不确定性队列`。队列只收录会改变原型方向、页面结构或交互路径的决策，不要求用户一次性评审所有细枝末节。

每轮只问队列中最高优先级的一个决策点，且该决策必须足以改变原型方向、页面结构或交互路径。不得把多个独立决策合并成一次批量确认问题。

队列优先级示例包括：

- 原型路线：HTML 原型、Stitch 原型，或组合路线（Stitch + HTML）。
- 页面/Frame 范围：需要哪些页面、弹窗、结果页或状态集合。
- 入口与信息架构：入口放在哪里，是否影响旧入口。
- 主流程：用户从入口到完成需要经历哪些关键步骤。
- 关键状态：必须覆盖哪些默认、错误、成功、权限、空、加载或部分成功状态。
- 字段与敏感信息：哪些字段必须展示、只读、派生、掩码或禁止展示。
- 交互红线：哪些路径、文案或功能绝对不能出现在原型里。

如果队列中的关键项已经在当前对话、`clarify.md` 或用户明确反馈中被确认，可以在 PRD 中写入并标注确认来源。未解决但不阻断当前 PRD 的事项，写入开放问题或假设；会阻断原型方向、页面结构或交互路径的事项，必须一次只问一个，或由用户明确接受为假设后才能继续。用户不需要确认每个示例数据、组件 gap、字段文案或状态微文案。

该章节必须用可执行的清单或表格写清：

- `页面/Frame 清单`：每个页面或弹窗的名称、目标、对应用户旅程/AC、入口来源和退出去向。
- `入口与信息架构`：入口放在哪里、按钮/菜单文案是什么、不能影响哪些旧入口。
- `主流程脚本`：评审人从第一步到完成要点哪些按钮、填哪些字段、看到哪些反馈。
- `状态覆盖`：默认、空、加载、错误、成功、权限/风控/配额等状态；每个状态触发条件和可见文案。
- `字段与数据样例`：真实领域字段、示例数据、必填/只读/派生规则、敏感字段展示规则。
- `组件与设计系统依据`：从项目 UI、现有页面、`DESIGN.md` 或组件库中可复用的布局、组件、token、图标；找不到时写“缺口”，不要发明。
- `Stitch 约束`：选择 Stitch 路线时必须明确目标 surface（web、mobile、响应式或指定设备）、screen/frame 范围、是否注入 `DESIGN.md`、MCP/SDK 不可用时是否等待修复或改批 HTML。
- `交互红线`：不得出现的路径、文案、页面职责或二义性，例如“不能新增只绑定不部署入口”“不能把 Trade Token 补填做进本期”。
- `开放问题`：只保留不会改变主流程和页面结构的问题；会改变页面/流程的问题必须先澄清。

下游 `$product:prototype`、`$product:stitch-prototype` 必须逐条消费该契约。若 PRD 只有用户故事、AC 和业务规则，没有原型约束契约，不得进入原型阶段。

写入 `prd.md`，把 PRD 状态设为 `Draft`。请求人批之前跑 `$product:review`。本会话没有该 skill 时，读 `../product-review/references/checklist.md` 按清单自查，结论仍写进 `## 对抗审查`。源头有更新就必须刷新看板 HTML：运行 `render_review_board.mjs`，确认 `.review-board/index.html` 存在。`portal_sync=bound_project` 时只调用 `portalHandoff`，记下未同步，不因写成 Draft 自动上传。

## 请求批准前自检

- 已执行公共契约中的批准前通用自检。
- 已按公共Wiki Context Gate核对项目上下文与跨仓边界，列实际已读页面、授权源码回查路径和知识缺口；PRD区分确认事实与待确认假设，不因缺Wiki自动生成。
- PRD 的背景、当前流程、范围、风险和验收标准引用了探索结果，而不是只复述澄清产物。
- 如果探索结果为空、不明确或冲突，已经先问用户一个澄清问题。
- 已记录 `product_mode`；如果为 `unknown`，PRD 未标记为 `Reviewed`，除非用户明确接受模式假设、风险、受影响范围，并明确允许本 PRD 阶段按该假设批准为 `Reviewed`。
- PRD：包含 `J → US → AC` 追踪矩阵、范围和非目标；涉及多角色交互、状态变化、命令执行或系统边界时，补充流程图、时序图、状态机或等价图示。
- 面向 UI/交互的 PRD：包含 `原型约束契约`，且页面/状态/字段/文案/设计系统依据足以约束后续 HTML 原型。
- 已跑 `$product:review`；源头有 `## 对抗审查`；有阻断发现时未请人批准。
