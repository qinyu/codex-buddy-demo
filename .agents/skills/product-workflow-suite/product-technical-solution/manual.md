# 技术方案设计指南

`product-workflow-0.9.3`

技术方案用于在动代码前，把架构、模块划分、接口契约、数据库迁移以及回滚步骤敲定。它要求助手必须基于本地代码库现状出具权威设计，严禁凭空写代码或脱离现实空想架构。

---

## 一、解决什么问题

需求进入开发阶段时，最怕直接上手写代码：
- 没有看清既有模块划分，把业务逻辑塞进不该放的目录，破坏原有的分层结构。
- 前后端接口字段全凭感觉命名，联调时才发现格式不匹配、缺少鉴权校验或缺少错误码定义。
- 数据库变更只写了 `CREATE TABLE` 或 `ALTER TABLE`，上线遇到问题没有可执行的回滚方案，导致生产数据损坏。
- 涉及复杂逻辑（如退款、核销、跨服务转账）时，缺少事务设计、接口重试幂等和降级保护，线上高并发下频频出现资损或脏数据。

技术方案阶段独立出具权威设计，强制在编码前把实现方案写透，由人类工程师审阅通过后，再指导后续的开发计划与实际编码。

---

## 二、怎么对助手开口

不需要输入机械命令或背诵复杂参数，在聊天框中直接用自然的工程师口吻表达：

```text
为刚刚定的支付退款需求设计技术方案，重点看数据库事务和接口重试。
```

或者明确关注点：

```text
按需求文档出一下技术方案，先探查现有订单和库存模块的代码，给出接口契约变更影响和数据库回滚步骤。
```

也可以指定重点审查的非功能需求：

```text
为用户实名认证功能写技术方案，重点评估现有权限拦截器复用、敏感信息加密存储以及高并发下的降级机制。
```

## 三、适用条件与裁剪红线

并非每一个需求都需要出具独立的技术方案。助手会根据代码改动影响主动建议，也可以根据以下规则判断：

| 场景类型 | 怎么处理 | 状态机标记与规则 |
|---|---|---|
| **复杂需求 / 跨模块 / 数据变更** | **必做核心**。包含新模块拆分、新接口定义、数据库表结构变更、权限或数据边界调整。 | 状态设为 `Draft`，生成完整方案，必须由你审阅并批准为 `Reviewed` 后方可开工。 |
| **小改动 / 无结构变更** | **可以裁剪**。没有新模块、没有新接口、没有权限或数据边界变化，原有架构完全覆盖。 | 在 `.workflow-state.json` 中将该阶段标记为 `Not Applicable`，并在原因中注明既有架构覆盖依据或已有方案路径。 |
| **轻量工作流 (Lite)** | **默认裁剪**。一天内单模块闭环的小需求。 | 状态直接标记为 `Not Applicable`，相关技术点简要写入开发计划中的验证说明即可。 |

## 四、关键产物：`technical-solution.md`

技术方案输出的核心产物是需求切片目录下的 `technical-solution.md`。

> 📌 **关键产物：`technical-solution.md`**
> 技术方案是后续开发计划（`development-plan.md`）和实际编码（`develop.md`）的技术依据。
> 方案出具后初始状态为 `Draft`。你审阅确认各项设计合理后回复 `批准`，状态才转为 `Reviewed`。

这份文档必须包含以下核心内容，缺少任一项都不得提交批准：

1. **当前系统上下文与代码探查证据**：
   列出本次改动实际检查过的本地源文件、配置路径、可复用的既有服务与类库。禁止脱离代码库空想。
2. **模块划分与组件边界**：
   清晰定义代码写在哪个目录、归属哪个服务、遵循什么分层，调用链路如何流转。
3. **前后端接口契约与变更影响**：
   给出精确的 API 路由、请求参数、字段级校验、鉴权规则、错误响应码。对存量接口的改动，必须逐项分析既有前端或调用方的向后兼容性。
4. **数据库变更与回滚步骤**：
   包含数据模型、状态机流转定义。必须同时提供正向变更脚本（如新增表、加字段、建索引）与明确的反向回滚脚本，确保发布失败时能无损退回。
5. **非功能设计**：
   包含核心链路的事务边界、重试与幂等策略、降级预案、可观测性（日志与监控指标）以及数据安全保护。
6. **基建现状评估**：
   包含单元测试基建现状与 Git 提交门禁现状，明确后续任务的前置准备。

## 五、核心机制与必须注意的高亮提示

助手在出具技术方案时，受严格的工程纪律约束：

### 1. 强制探查代码库，严禁空中造楼
出具架构方案前，助手必须实际检索并读取当前仓库的源码、路由定义、数据库迁移脚本、依赖配置文件与测试文件。如果助手无法访问目标代码库，必须在文档开头明确声明，并将所有文件路径和模块划分标为未核实的假设，先向你提问澄清，绝不能凭空捏造不存在的类、包路径或 API。

> 💡 **单测基建缺口与 Git 门禁缺口的识别机制**
> 助手在探查代码库时，会主动检查两个关键工程门禁：
> 1. **单元测试基建**：检查仓库是否有测试框架（如 pytest、Jest、JUnit）、能否直接运行测试命令、能否产出 `junit.xml` 和覆盖率报告。如果发现当前仓库完全缺少测试环境，方案中会单独列出「单元测试基建缺口」章节，建议在后续开发计划中先调用 [$unit-test-init](unit-test-init.html) 准备环境。但这**属于建议项，不阻塞技术方案本身的产出与批准**，不会强行暂停流程去安装依赖。
> 2. **Git 门禁基建**：检查仓库是否有 Git Hook 管理工具（如 Lefthook、pre-commit、Husky）以及提交前、推送前的代码检查。如果缺少门禁，方案中会记录「Git Hook 质量门禁缺口」，建议后续使用 [$git-hook-init](git-hook-init.html) 配置。同样，这只作为后续任务建议，不阻塞当前方案。

> ⚠️ **严禁私自下载新 SDK 或升级框架主版本**
> 编写技术方案时，助手严禁自行决定引入未曾使用过的新第三方 SDK、重量级组件或升级底层框架的大版本（例如将 Spring Boot 2 升到 3，或将 Vue 2 升到 3）：
> - 引入新依赖会增加团队维护成本、带来供应链安全漏洞风险，并可能导致企业私有镜像源拉取失败。
> - 框架大版本升级伴随着大量底层 API 废弃与破坏性变更，极易引发其他存量业务模块崩溃。
> 方案必须优先复用仓库现有依赖与工具库。如果业务场景确实必须引入新依赖或升级版本，方案必须将其作为重大技术决策单独列出，写明引入原因、包体积影响与兼容性风险，并由人类工程师在评审中明确确认。

## 六、助手提问时你怎么配合

如果助手在探查代码后发现需求存在未决的关键工程决策，会先停下来向你提问，例如：

- *“在现有代码中，支付状态流转由消息队列驱动，但需求文档提到希望前端轮询接口，本次是沿用队列还是新增查询接口？”*
- *“当前订单表数据量已达千万级，本次加字段是否走在线 DDL 工具，还是直接跑普通迁移脚本？”*

遇到这类提问，不要有心理负担，根据你的实际运维与生产要求，用一两句话直接回复即可：
- `沿用现有消息队列，前端只对接现有的查询接口即可。`
- `用公司现有的 gh-ost 工具做在线变更，方案里写清楚 DDL 语句就行。`

确认完毕后，助手会继续完成方案并生成 `.review-board/index.html` 评审看板，供你最终审阅。
