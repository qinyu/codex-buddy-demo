# 决策记录：XAML / WPF 是否纳入覆盖范围

**决策**：不纳入。graphify 及其 XAML 分支已整体移除，不保留第二套引擎。
**日期**：2026-09-20（替换 0.7.x 起依赖 `has_xaml()` 触发 graphify 的做法）
**状态**：已实施，**可重评**（重评条件见文末）

## 为什么去掉

1. **两套引擎要同时维护**：主路径是 CodeGraph，XAML 走 graphify，等于两条适配、两套降噪、两个本机缓存目录（`.codegraph/` 与 `graphify-out/`）。
2. **触发条件不稳**：`has_xaml()` 按文件后缀决定要不要多跑一个工具，同一个团队的不同仓会走不同路径，排查和复现都变复杂。
3. **主路径已能覆盖 C#**：CodeGraph 语言表里 C# 是 Full support，`.cs` 全进图。

## 代价（实测，不是估计）

WPF 替身仓 Flow Launcher，2026-09-20 实测：

| 项 | 数值 |
|---|---|
| 盘上 `.cs` | 388 文件 / 64,403 行 |
| 盘上 `.xaml` | 393 文件 / 55,080 行 |
| **未覆盖的 `.xaml`** | **文件占 50.3%；代码行占 46.1%** |
| 图里覆盖 | 408 files（csharp 388 / yaml 14 / xml 4 / python 2） |
| 另有 `.xaml.cs`（code-behind） | 55 文件 / 7,829 行，**作为 `.cs` 已覆盖** |

**体量上这不是小数目**：在一个真实 WPF 应用里，XAML 接近一半代码量。
之前以为「XAML 只是少量标记」是错的——文件占比与行数占比几乎一致（50.3% / 46.1%）。

丢的具体是什么（同一样本文件取证）：

| 查什么 | 结果 |
|---|---|
| `BtnCancel_OnClick`（XAML 里 `Click="..."` 指向的处理器，定义在 `.cs`） | 10 命中 —— **实现侧有覆盖** |
| `RelativeSource`（绑定相关） | 0 命中 |
| 图里 `filePath` 以 `.xaml` 结尾的节点 | **0** |

归纳：

- **保留**：ViewModel、服务层、code-behind 方法体（含 55 个 `.xaml.cs`）—— 业务逻辑的实现全在 `.cs` 里
- **丢失**：393 个 `.xaml` 文件（约 46% 代码行）；`{Binding X}` → ViewModel 属性的**绑定边**；`Click="..."` 的**事件接线边**（处理器本身在图里，但 XAML 指向它的那条边没了）；资源、样式、模板、页面导航结构

**一个容易漏的点**：XAML 不全是布局。`Visibility="{Binding CanSubmit}"`、`IsEnabled="{Binding ...}"`
这类绑定其实是**界面化的业务状态**，它们也在丢的那一半里。所以不能说「XAML 里没有业务」。

一句话：**丢的是界面层、它的接线，以及写在界面上的那部分状态规则；
方法的实现没丢。**

## 对客户现场意味着什么

C#/WPF 项目同样适用。分场景看：

| 用途 | XAML 缺失的影响 |
|---|---|
| 追方法实现（“这个怎么算”） | **小**，`.cs` 侧够用 |
| 找需求出处（“这段原来写在哪”） | **小到大**，需求文字走 RAG；但要回到界面锚点时不够 |
| 迁移 MES(.NET) → Java 微服务 | **小**，WPF 视图本就要重写成 Web，XAML 不是迁移输入 |
| 改界面 / 追界面链路（“这个按钮点了走哪条”） | **大**，直接断链 |
| 查界面上写的状态规则（`Visibility`/`IsEnabled` 绑定） | **中**，这类“界面化业务状态”也在丢的那一半里 |
| LLM Wiki 写 WPF 模块页 | **中**，入口往往是一个 `xaml + xaml.cs` 对，入口会指不到 |

**因此结论分两头**：

- 如果主要用途是**迁移与后端逻辑理解** → 当前取舍可接受；
- 如果团队日常大量工作是**改 WPF 界面**（不像迁移项目那样“视图反正要重写”）→ 代价就变重，46% 的代码行没有结构支撑。

**前置确认（真实仓复测时先做）**：业务锚点是否从**界面入口**起追。
锚点在 Service / Handler / Controller → 可接受；
锚点必须从 XAML 起（按钮、页面、导航）→ 需另找补 XAML 的方案。

## 什么条件下应重评

满足任一条，就回来推翻这个决策：

1. 客户现场确认**业务链路必须从界面入口起追**，且占比不低；
2. 出现能同时覆盖 `.cs` 与 `.xaml` 的**单一引擎**（不必再维护两套）；
3. CodeGraph 自身开始支持 `.xaml`（升级版本后重跑 `codegraph status` 看 `Files by Language` 是否出现 xaml）；
4. 复测发现 `.cs` 侧覆盖不如预期，导致「界面到逻辑」这一段两头都缺。

重评时先跑一次量化：拿一个有 XAML 的仓，对比「盘上 `.xaml` 数」与「图里 `.xaml` 节点数」，再决定是补工具还是改锚点策略。
